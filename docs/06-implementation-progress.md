### Found while implementing TENANT-008

**Onboarding a clinic with an Arabic branch name lost the admin password.** The command committed the transaction, then crashed printing the branch name — Windows consoles default to cp1252, which cannot encode Arabic. The generated password was printed *after* that line, so it was never shown, and it is not recoverable. In an Arabic-first app that is the ordinary case, not an edge case.

Fixed two ways, because either alone would be fragile: the command forces its output stream to UTF-8, **and** credentials are now printed before any user-supplied text, so an unrecoverable secret never sits behind something that might fail to render. Both are covered by regression tests.

### Found while implementing SEC-011

1. **Every unmatched URL was returning a 500.** The catch-all in `project/urls.py` did `redirect('login')`, but that route is namespaced `accounts:login`, so it raised `NoReverseMatch`. Latent for a long time, but the hard cut makes it the landing place for every stale bookmark — fixed to `accounts:login`, and stale URLs now redirect cleanly.
2. **The appointment screens displayed the raw database id labelled "رقم التذكرة"** (ticket number) — in `detail.html`, `delete.html`, `update.html`, a success message, and the visit table on `patients/detail.html`. `serial_number` has existed for exactly this. Now shows the serial.
3. **The migration trap fired, and not quite as predicted.** `AddField` with `default=uuid.uuid4` writes *one* value to every existing row — so the rows were non-null and identical, and the `uuid__isnull=True` backfill matched nothing, failing on the unique constraint. The `AddField` has to carry no default at all; the default arrives with the closing `AlterField`. Caught by running the migration against the seeded database rather than an empty one.
4. `project/urls.py` also contains an unreferenced `home_redirect` carrying the same un-namespaced bug (`redirect('dashboard')`). Left alone — dead code, and wiring it up is a separate decision.

### Found while implementing TENANT-005/006

Switching the default manager to fail closed exposed a cross-tenant leak already latent in the scheduled reports, plus two paths that would have gone silently empty:

1. **`reports/views.py` would have emailed one tenant's revenue to another's recipients.** Both the branch loop (`Branch.objects.all()`) and the recipient list spanned the whole database. As soon as a second tenant existed, every tenant's daily/monthly/annual figures would have gone to every active `ReportRecipient` — across clinics. All three generators now loop over tenants and do their work inside `tenant_context`, which scopes branches and recipients automatically.
2. **The two `post_migrate` seeding hooks** run with no tenant in context, so they now read through `all_objects` — otherwise the `get_or_create` lookup finds nothing, tries to insert, and collides with the row that already exists.
3. **Django admin** would have shown empty changelists for all 15 tenant-owned models, since admin reads `_default_manager`. `TenantOwnedAdmin` in `tenants/admin.py` reads `all_objects` instead. This mattered more than it looks: `PaymentMethod` and `SalaryType` have no views at all and are *only* manageable through admin.

Existing tests needed the same treatment — fixtures build data for two tenants from outside any request, so they use `all_objects` deliberately rather than relying on ambient context.

### Found while implementing TENANT-002

Making `tenant` required surfaced four write paths that would otherwise have broken at runtime rather than at review:

1. **Two `post_migrate` seeding hooks** create tenant-owned rows — `accounts/apps.py` (Admin/Reception roles) and a second one in `employees/apps.py` seeding the "Doctor" `EmployeeType` that `Appointment.doctor` depends on via `limit_choices_to`. Both would have broken `migrate` itself. Now seed per tenant; they move into tenant provisioning at TENANT-008.
2. **`notifications/signals.py`** creates a `Notification` per user on every appointment and payment — needed the tenant threading through.
3. **11 create views** had to set `tenant` explicitly before saving. Interim by design: TENANT-005/006 will assign it automatically from request context, and these lines then get deleted.
4. **`employee_create` needed `form.save_m2m()`** once it switched to `commit=False` — without it the employee's specializations would have been silently dropped on every create.

*(Superseded by TENANT-003 below, which removed the global unique constraints that made those seeding hooks single-tenant-only. One correction to an earlier note here: `EmployeeType.name` was never globally unique — only `ClinicRole.name` was.)*

### FE-016 — Arabic cannot be rendered in exported PDFs

**The defect.** `utils/utils.py::export_pdf` builds every document with `Helvetica-Bold` and registers no other font. Inspecting the produced file confirms it: the only embedded fonts are `Helvetica`, `Helvetica-Bold` and `ZapfDingbats`, all Latin-only Type 1 fonts with no Arabic glyphs. Arabic text is therefore drawn with a font that cannot represent it.

**It cannot be fixed with anything already in the repository.** The obvious repair — register the bundled `static/fonts/sourcesanspro/Cairo-Regular.ttf`, which the dead `utils/export_pdf.py` already tries to use — does not work. Asking reportlab for the glyphs directly:

| codepoint | character | glyph |
|---|---|---|
| U+0623 | أ | **none** |
| U+062D | ح | **none** |
| U+0645 | م | **none** |
| U+0041 | A | 37 |

Cairo is normally an Arabic Google font, but this 30 KB copy is a **Latin-only subset with 215 codepoints**. Auditing all 22 font files under `static/` (via fontTools, installed temporarily and removed again — the project venv still matches `requirements.txt` exactly): **not one contains a single codepoint in the Arabic block U+0600–U+06FF.** Source Sans Pro covers 1298 Latin codepoints; the Material Design icon font covers 3997 icons; neither has Arabic.

**Impact.** Four user-facing "تصدير PDF" buttons — patients list, payments list, financial report, services list. Every one exports Arabic content: patient names, service names, and the report title itself (`قائمة المرضى - فرع …`). The failure is silent: the button returns a valid, well-formed PDF with blank or box glyphs where the data should be, which staff could print and file without noticing. **Excel export is unaffected** and sits beside every PDF button — `openpyxl` embeds no fonts, so Arabic round-trips intact (asserted in `dashboard/test_exports.py`). So there is a working path today.

**A second, milder finding from the same audit.** Six templates declare `font-family: 'Cairo', sans-serif`, but there is **no `@font-face` rule for Cairo anywhere** and it is never referenced through `{% static %}` — only Source Sans Pro is declared. The browser therefore looks for a locally installed "Cairo" and silently falls back to the system `sans-serif`. Arabic still displays in the browser because the operating system supplies a font, so this is cosmetic rather than broken — but the app's typography is machine-dependent, and the `'Cairo'` declaration is inert.

**Options, none applied:**

1. **Add a real Arabic font** (e.g. the full Cairo or Noto Naskh Arabic, ~200–400 KB, SIL Open Font License), register it in `export_pdf`, and use it for the table and title styles. This is the only option that makes the existing buttons work. It requires a deliberate choice of font and licence, and adding a tracked binary — which is why it is not done here.
2. **Also fix the shaping.** Even with an Arabic font, reportlab draws unshaped, left-to-right text: Arabic letters would appear in isolated forms and reversed order — present but wrong. Correct output needs bidi reordering and contextual shaping. reportlab 5 exposes these as extras (`rlbidi` for bidi, `uharfbuzz` for shaping), which is new capability from the DEP-002 bump; previously it needed `arabic-reshaper` plus `python-bidi`. Either way it is two more dependencies.
3. **Remove the PDF buttons** and keep Excel, which already works. The cheapest honest option if Arabic PDFs are not actually needed.
4. **Fail loudly** rather than emit a silently unreadable document. Worth doing whichever of the above is chosen, but on its own it turns a working-looking button into an error, which is a product decision.

**Recommendation: 1 + 2 together, or 3.** A half-fix — an Arabic font without shaping — produces a document that looks repaired while being unreadable, which is worse than the current state because it invites trust.

### FE-016 resolution — what the investigation actually found

Option 1 + 2 was approved and implemented. Three findings changed the shape of the work along the way.

**Dead end 1: reportlab 5's own `bidi` extra does not exist.** `pip install reportlab[bidi,shaping]` fails — the extra requires `rlbidi`, and *"No matching distribution found"*: it is not on PyPI at all. Only `uharfbuzz` (the `shaping` extra) is available, and shaping without bidi still draws right-to-left text in reverse. So the reportlab-native route from the earlier writeup was unusable, and the established `arabic-reshaper` + `python-bidi` pair was used instead. `arabic-reshaper` is pure Python; `python-bidi` is a compiled Rust extension that publishes **manylinux wheels for CPython 3.11, 3.12 and 3.13** — verified, because a Linux deploy without a build toolchain would otherwise fail at install.

**Dead end 2: Google Fonts publishes no static Cairo.** `ofl/cairo/` in the canonical `google/fonts` repository contains only `Cairo[slnt,wght].ttf`, the variable font, plus `OFL.txt`. Both the `static/` subdirectory and the `fonts.google.com/download` API returned HTML rather than a font. reportlab registers the variable font and embeds its default instance (weight 400, slant 0 — the Regular face), which is what the tests confirm. Provenance, size and SHA-256 are recorded in `static/fonts/cairo/README.md`, which is what P0 asked for before a vendor binary is tracked.

**The silent failure the obvious fix would have shipped.** Having an Arabic font is *not* the same as being able to draw the shaped output, and the difference is invisible. `arabic_reshaper` maps letters onto Arabic Presentation Forms-B (U+FE70–FEFF). Cairo covers 89 of those, but modern fonts implement *isolated* forms through the base codepoint plus OpenType GSUB rather than duplicating them — so **17 codepoints the reshaper emitted had no glyph in Cairo**: `أ ا ب ة ت ج د ذ ر ط ع ل م ن و ي` in isolated position, hitting strings as ordinary as `أحمد محمد`, `إجمالي الإيرادات` and `القاهرة`. Each would have rendered blank in a valid-looking PDF. Configuring the reshaper with `use_unshaped_instead_of_isolated` leaves them as base codepoints, which Cairo has, bringing missing glyphs to **zero across a 66-string corpus** drawn from the app's real titles, headers, diagnoses, medications, allergens, branch names and status labels — plus money, phone numbers and serials, which must pass through untouched.

**Also fixed:** the document is now laid out right-to-left to match `<html lang="ar" dir="rtl">` — right-aligned metadata, and **table columns reversed** so the first header sits on the right where an Arabic reader starts. Header and body are reversed together, so a cell never parts company with its column. The header row no longer uses `Helvetica-Bold`: Cairo is the only embedded face with Arabic, so a Latin header font is exactly how the bug reappears.

**A gap in the first version of these tests, worth recording.** Asserting that the PDF embeds Cairo does **not** prove the table uses it — the title alone embeds the font, so reverting the header row to `Helvetica-Bold` passed the embed check while every header cell rendered blank. The mutation test caught that the tests did not catch it. `arabic_table_style()` was therefore extracted so a test can assert every `FONTNAME` in it is the Arabic face, and that one command spans the whole table including row 0. Both mutations now fail the suite.

**Cleanup, done as a separate change (FE-017):** `static/fonts/sourcesanspro/Cairo-Regular.ttf` — the Latin-only 215-codepoint subset that caused the confusion — and the dead `utils/export_pdf.py` that was the only thing referencing it are both removed. There is now exactly one Cairo in the repository, so the name cannot mislead the next person. The three live callers (`billing`, `patients`, `services`) all import from `utils/utils.py` and were unaffected; the `sourcesanspro/` directory keeps its own 24 Source Sans Pro files, which the CSS `@font-face` rules do use.

### Findings from the data compatibility audit

Against the local SQLite database: **2 blockers, 0 warnings.** Both are `max_length` overflow on phone columns — 1 row in `branches_branch.phone` (21 chars) and 8 rows in `patients_patient.phone1` (up to 22 chars), against `varchar(20)`. **Remediation — option 1 chosen and applied (DATA-002 below).** The alternatives were:

2. Re-seed the demo data — clears the 9 rows locally, useless for real records.
3. Per-record review before import — still required for the real database once located, but it does not fix the column.

| SAAS-001 | `Plan` — the catalogue (§11) | DONE | Platform-level and deliberately **not** tenant-owned: it has no tenant column, so `tenants/rls.py` skips it automatically, which is correct — a plan is not anybody's private data. §11's two kinds of allowance are modelled differently because they behave differently. **Limits** (branches, doctors, staff, patients, storage) are columns, since they are a fixed short list and columns make "which tenants are near their patient limit" an ordinary query. **Features** are JSON, because §11 ends its list with "other features" and a fixed set of columns would mean a migration every time sales invents a package. `None` on a limit means unlimited rather than a large sentinel — "unlimited" and "a million" are different statements, and only one survives a customer with a million patients. Seeded with Basic / Professional / Enterprise |
| SAAS-002 | `Subscription` — what a tenant pays for | DONE | Tenant-owned and therefore RLS-protected: a clinic sees its own terms and nobody else's. Kept as a **history** rather than a field on `Tenant`, because clinics upgrade, lapse and renew and billing needs to answer "what were the terms in March". Two database constraints carry rules the application should not have to remember: only **one active subscription per tenant** (two would make entitlement resolution silently pick whichever sorted first) and `ends_on >= started_on`. `feature_overrides` is how §11's "custom contracts" work without inventing a private plan for every negotiation. The consequence of RLS here is that genuinely cross-tenant billing queries (§47 subscription revenue) need the per-tenant loop — the same trade already accepted for platform admin |
| SAAS-003 | Entitlements, enforced server-side (§84) | DONE | A registry of feature keys with a resolution order of **plan → tenant override**, and limits checked on the way in. Everything **fails closed**: a tenant with no active subscription gets a limit of **0, not unlimited** — treating "unknown" as "unrestricted" is precisely how a lapsed customer grows without bound — an unknown feature key raises rather than returning a quiet `False` that would read exactly like a disabled feature, and only an `active` subscription counts. Enforcement is on the POST in `branch_create` and `patient_create`, not on a hidden button: the form posts perfectly well without the button. Applied to two views as the pattern; the remaining limits (`max_doctors`, `max_staff`, `max_storage_mb`) attach the same way. Three mutations verified: making a missing subscription unlimited, counting cancelled subscriptions, and removing the server-side check each fail the suite |
| SAAS-004 | Grandfathering existing tenants | DONE | **The migration that would otherwise have broken every running clinic.** Because entitlements fail closed, shipping enforcement against tenants that have no subscription row would have set every limit to zero — no new branch, no new patient, from the moment it deployed. `subscriptions.0002` therefore seeds the catalogue *and* puts every existing tenant on Enterprise (unlimited, all features), with a note on each subscription saying exactly why. Deliberately generous: guessing a smaller tier would break somebody's day, and a downgrade is a commercial decision for a person who knows the contract. The migration binds the tenant GUC around each insert so it works whether or not the RLS policies are already installed — the ordering happens to be safe today, and relying on that would be a trap for whoever reorders next |
| BUG-003 | Audit signal broke a data migration | DONE | Found by SAAS-004 and the same family as BUG-001. `create_audit_log` assigned `tenant=instance.tenant`, but inside a data migration the instance is a **historical** model from `apps.get_model`, so its `.tenant` is a historical `Tenant` that Django refuses to assign to a relation declared against the real one — `ValueError`, and the migration dies with it. Now uses `tenant_id`, which is an integer and works for both, and saves fetching the related row. Any future data migration touching a tenant-owned model would have hit this |

| BUG-004 | RLS hides rows from Django's own deletion collector | DONE | Found when `seed_demo --reset` started failing with a **raw foreign-key violation** where a clean `ProtectedError` was expected. `Subscription.tenant` is `PROTECT`, so deleting a tenant that still has one should be refused by the ORM. It was not, and the reason is a consequence of RLS worth writing down: Django's deletion collector reads related rows through `_base_manager` — which is `all_objects` here — and under row-level security an **unbound** query returns nothing. So the collector concluded there was nothing protecting the tenant, issued the DELETE, and PostgreSQL raised the constraint itself. The application-level guarantee silently degraded into a database error. This is the same lesson as the reverse-accessor and empty-dropdown traps, arriving in Django's internals rather than in our code: **anything that reads tenant-owned rows outside a bound connection sees nothing**, including framework machinery. Fixed by deleting subscriptions inside the per-tenant binding like every other tenant-owned table. Worth remembering for any future `PROTECT` relation on a tenant-owned model |

| SAAS-005 | Platform admin + Tier 1 "act as tenant" (§10) | DONE | The deferred answer to ADMIN-002, built as agreed: **no BYPASSRLS role, no second database connection, no bypass flag.** Platform staff select one clinic explicitly and the views enter `tenant_context` for a single read on the **ordinary** connection, so row-level security applies to them exactly as it does to that clinic's own staff. The isolation invariant is untouched — a connection is still always bound to exactly one tenant. **`TenantMiddleware` was deliberately not modified.** It derives the tenant from `request.user` and nothing else, on the stated grounds that reading it from a header, parameter or session would turn switching clinics into a one-line attack; teaching it to honour a session value would put exactly that mechanism into every request in the application. The inspection views bind their own context instead, for the duration of one read, and a test asserts the binding does not survive the request. Access requires `is_platform_staff` **and no tenant** — a user who belongs to a clinic never holds platform powers even if the flag is set by mistake — and explicitly **not** `is_superuser`, which is a Django-admin concept and conflating the two is how a tenant administrator eventually acquires cross-tenant reach because somebody ticked a box on the wrong screen. Refuses with 403 rather than redirecting to login, which would confirm the URL exists and bounce an already-authenticated user to a page they are past |
| SAAS-006 | Tenant lifecycle and subscription management (§10) | DONE | Suspend/activate writes to `Tenant`, a platform model with no isolation policy, so it is the platform changing its own record of a customer rather than cross-tenant access to clinical data. Changing a clinic's plan is **the only tenant-owned write available to platform staff**, kept narrow on purpose: it moves an existing subscription between plans and touches nothing else, because that is the commercial relationship and not a patient record. Both are POST-only: a GET would let a crawler or a prefetched link suspend a clinic. **Clinical data stays read-only from the platform area**, and that is asserted as the absence of routes rather than assumed — a test pins the complete route list, so a third write cannot appear without someone deciding to change that test |
| SAAS-007 | Platform actions are audited | DONE | Reads are recorded, not just writes: the sensitive act is a SaaS operator opening a clinic's record at all, and the change-tracking signals in `audit/` only fire on save and delete, so an inspection would otherwise leave no trace. Entries are filed against the **inspected** tenant rather than the operator (who has none), so the fact that the platform looked appears in that clinic's own trail, which is where a customer would go looking for it. Status and plan changes record **both the old and the new value**, because "who suspended this clinic and when" is the first question asked afterwards and the previous value is half the answer. Unlike the signal-based auditing elsewhere, a failure here propagates rather than being swallowed — elsewhere losing an audit row beats failing a clinician's save, but here the audit *is* the control, so an inspection that cannot be recorded should not happen. A test caught that a write produces **two** entries (the signal's data change and this module's platform action) and asserts both, since losing either leaves a different question unanswerable |

### Found while implementing treatment sessions

**`PROTECT` on the new models silently broke `seed_demo --reset`, and would not have shown up until plans existed.** `TreatmentPlan.patient` and `TreatmentSession.patient` are `PROTECT` (medical retention, MED-003), so patients can no longer be cleared while either exists — and sessions must go before plans. The first reset after adding the models still passed, because nothing had created a plan yet. Fixed the ordering and then seeded plans and sessions deliberately, so the reset path is exercised: two consecutive `--reset` runs now produce identical counts instead of colliding.

**`TreatmentPlan.completed_sessions` returns 0 outside a request rather than raising.** `plan.sessions` is the tenant-scoped reverse accessor, so the same fail-closed trap that hides reverse accessors from management commands also silently zeroes this figure. Hit while smoke-testing against seeded data — the progress read "0 of 6" until the read was moved inside `tenant_context`. Recorded on the property itself, since a count that is quietly wrong is worse than one that fails.

**Verified against seeded data, not only tests**: every plan and session page returns 200 for the demo doctor and redirects Reception, and a seeded pulse-priced session shows 25 × 300 = 7500. Noted while doing it: a doctor can open a plan whose patient's *file* returns 404, when the plan's branch is theirs and the patient was registered at another branch. That is pre-existing branch-scoping behaviour — `Visit` has always worked the same way — not something these models introduced, so it is left alone rather than changed under a clinical-domain commit.

### Found while implementing treatment plans

**RLS membership is now derived from the models, not listed.** `tenants.0005` worked from a hand-written list of 19 tables, and adding `TreatmentPlan` left that list stale — a tenant table with no policy and nothing to say so. That is the realistic way this protection decays: not someone deleting a policy, but someone adding a model and nobody noticing. `tenants/rls.py` now derives the set from the model registry (a non-nullable `tenant` FK, which is exactly what `TenantOwnedModel` gives every subclass), `tenants.0006` reapplies it idempotently, and `tenants/test_rls.py` derives its expectations the same way — so a tenant-owned model added without a policy fails the suite instead of shipping unprotected. Confirmed against the real database: `medical_treatmentplan` came out `ENABLE`d, `FORCE`d and carrying `tenant_isolation` without anyone naming it.

**`timezone.localdate` cannot be a field default in this project.** It raises `ValueError: localtime() cannot be applied to a naive datetime`, because `USE_TZ = False` makes `timezone.now()` naive. Replaced with a named module-level `medical.models.today` (a field default has to stay importable for migrations).

**The interpreter in use is Django 5.2; `requirements.txt` pins 4.2.** Every earlier verification in this project ran on whichever happened to be active, and the generated migration header says "Generated by Django 5.2". The suite is now confirmed green on **all four** combinations — {Django 4.2, 5.2} × {PostgreSQL 17.11, SQLite}, 154 tests each — so nothing here depends on the difference. But the pin and the environment still disagree, and production installs from `requirements.txt`: one of the two should be made authoritative before deploy.

### Found while implementing the clinical domain

**Every dropdown on every form had been empty since TENANT-006.** `ModelChoiceField` builds its queryset when the form *class is imported* — long before any request — so the tenant-scoped manager resolved with no tenant in context, failed closed, and baked `.none()` into the field permanently. Nobody could create an appointment, payment, expense or employee through the UI.

**Reverse related accessors are tenant-scoped too.** `prescription.items` inherits the scoped manager class, so outside a request it returns nothing — the same fail-closed trap as the form querysets, in a different disguise. Correct inside a request; a landmine for management commands and background jobs, which must enter `tenant_context` or use `all_objects`. Pinned by a test so the next person meets it as documented behaviour rather than a mystery.

**`scoped_to_user` assumed every clinical model has a `branch` field.** `Prescription` doesn't — it inherits the branch of the visit that issued it — so the helper now takes a lookup path.

The form-queryset bug above was invisible because the only tests touching those forms asserted they were *invalid* — `test_payment_form_rejects_negative_amount` was passing for entirely the wrong reason. Fixed with `TenantScopedFormMixin` (`tenants/forms.py`), which rebinds relation querysets per instance at request time, reconstructing them the way `ForeignKey.formfield()` does so `limit_choices_to` survives. Applied to all 14 ModelForms, with regression tests asserting choices are actually *populated* and still tenant-scoped.

## Deploy note for SEC-009 — existing staff log in differently afterwards

`accounts.0005_email_login` makes email the login credential. Accounts created under the old username-based login may have a blank or duplicated email, so the migration backfills before applying the unique constraint:

- A blank email, or one that collides with an earlier account (case-insensitively), is replaced with `username@tenant-slug.local`.
- The migration prints every address it generated. **Those placeholders are the new login credentials** — the account stays reachable, but the address should be replaced with a real one.

Verified by simulation against four legacy accounts — two with no email, two differing only by case: the first keeps its address, the other three get placeholders, and all four end up unique.

## Production-deploy caveat for INFRA-001 (read before running `migrate` on the live server)

> **Superseded in part by the Gate A findings (2026-09-09): there is no reachable production server.** `passenger_wsgi.py` has been entirely commented out since 2025-09-29, `2odays.com` does not resolve (public DNS returns SERVFAIL), no Passenger config has ever been tracked here, and `club-ft.com` is a different project. **The location of any real patient data is unknown, and nothing below should be executed until that is confirmed.** The schema-drift reasoning that follows remains correct and applies to whatever database is eventually identified.

These `0001_initial.py` migrations were generated from the **current** `models.py` files, not from whatever schema history actually produced the live production database (which had no tracked migrations at all until now). If the production DB's real schema exactly matches what's in `models.py` today, running `python manage.py migrate --fake-initial` on production will mark these as applied without re-running the `CREATE TABLE` statements, which is the correct move. If the production schema has drifted from `models.py` in any way not visible in this repo, that mismatch needs to be resolved (compare schemas, or hand-adjust the generated migration) before running `migrate` there — running a plain `migrate` on a database that already has these tables will fail with "table already exists" without `--fake-initial`.
